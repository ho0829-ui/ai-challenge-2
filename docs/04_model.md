## VLM과 PEFT·LoRA의 관계

VLM은 시각 정보를 언어 처리와 결합해 질문과 보기를 판단합니다. PEFT(Parameter-Efficient Fine-Tuning)는 전체 모델의 많은 파라미터를 갱신하는 대신 제한된 파라미터를 학습하는 방법들의 범주입니다. LoRA(Low-Rank Adaptation)는 그중 선형 가중치의 변화량을 저랭크 행렬의 곱으로 표현하는 방식입니다.

입력 열벡터가 `x ∈ R^{d_in}`, 원래 선형 가중치가 `W ∈ R^{d_out × d_in}`라면 다음처럼 씁니다.

$$
W' = W + (\alpha/r)BA,
\qquad A\in\mathbb{R}^{r\times d_{in}},\quad B\in\mathbb{R}^{d_{out}\times r}.
$$

원래 W를 고정하고 A·B를 학습합니다. 원래 행렬의 파라미터 수는 `d_out × d_in`, LoRA의 수는 `r(d_in+d_out)`입니다. rank r은 변화량의 표현 용량과 학습 비용을 조절합니다. r이 크다고 검증 성능이 반드시 좋아지는 것은 아닙니다. alpha는 보통 `alpha/r` 배율에 영향을 주며, dropout은 학습 중 어댑터 입력 일부를 버리는 정규화 설정입니다.

이 프로젝트의 기본 설정은 `r=32`, `alpha=64`, `dropout=0.05`이므로 표준 스케일은 2입니다. 모든 층과 모든 파라미터에 같은 크기의 변경을 강제한다는 의미는 아닙니다. 일반적으로 LoRA는 학습 파라미터·어댑터 저장량을 줄이지만 모델 본체를 메모리에 로드하는 비용까지 없어지는 것은 아닙니다.

근거: 코드 전용 셀 4·7; 일반 개념은 [Microsoft 공식 LoRA 구현·논문 안내](https://github.com/microsoft/LoRA)를 확인했습니다. Full fine-tuning과 직접 비교한 실험은 제공되지 않아, 이를 하지 않은 개인적 이유나 동일 정확도 보장은 주장하지 않습니다.

## Qwen 코드에서 확인한 학습

`target_modules`는 이름에 `visual`이 있는 모듈을 제외하고 `q_proj/k_proj/v_proj/o_proj/gate_proj/up_proj/down_proj`로 끝나는 모듈을 선택합니다. 따라서 제공 코드의 의도는 시각 모듈을 제외한 attention·MLP 선형층 LoRA입니다. 실제 학습 가능 파라미터 수 출력은 저장되어 있지 않습니다.

| 설정 | Q | HR |
|---|---:|---:|
| epoch | 1 | 2 |
| 미니배치 | 4 | 4 |
| gradient accumulation | 2 | 4 |
| 명목 실효 배치 | 8 | 16 |
| 기본 추론 배치 | 16 | 32 |
| 기본 TTA 횟수 | 2 | 2 |

공통은 lr `1e-4`, AdamW, weight decay `0.0`, cosine schedule, warmup `0.05`, gradient clipping `1.0`입니다. 마지막 짧은 배치와 accumulation 경계에서는 실제 표본 수가 명목치와 달라질 수 있습니다. `GRAD_CKPT=False`, `QUANT_4BIT=False`가 기본입니다. 4bit 분기 코드는 존재하지만 실제 사용 기록이나 필요 패키지 검증이 없으므로 사용했다고 표현하지 않습니다.

학습 중 각 행의 보기를 무작위 순열로 바꾸고, 정답 인덱스를 그 순열에서의 위치로 바꿔 교차 엔트로피를 계산합니다. 매 epoch `n_tta=1` validation으로 체크포인트를 선택합니다. 최종 추론의 TTA 2와 체크포인트 선택의 TTA 1은 구분해야 합니다.

최종 발표 슬라이드 4의 “실효 배치 8”은 Q 코드와 맞지만 HR 코드의 16과 다릅니다. Gemma의 1 epoch, 공유 MLP·attention만 LoRA 대상으로 삼았다는 설명도 그 슬라이드에서 확인되나 구현이 없으므로 검증 완료로 표기하지 않습니다. Gemma 3D MoE 전문가를 제외했다는 설명은 자료의 주장으로 남깁니다.

## 시각 토큰은 픽셀 해상도와 다르다

Qwen은 프로세서의 `patch_size × merge_size`를 `PS`로 읽습니다. 코드 주석은 `16 × 2 = 32`라고 설명합니다. 이미지 크기 w·h와 목표 토큰 t에 대해 `s=sqrt(t×PS²/(w×h))`를 계산하고, 가로·세로를 PS의 배수로 반올림해 리사이즈합니다. t는 **시각 입력 면적의 예산**이며 텍스트 토큰 수나 고정 가로·세로 길이가 아닙니다.

PS가 32이고 정사각형이라는 단순 근사에서 1024토큰은 한 변 약 1024픽셀, 1280토큰은 약 1145픽셀입니다. 실제 종횡비·반올림·프로세서 처리에 따라 달라집니다. 초기 발표 슬라이드 3의 “1280토큰 ≈ 1024×1024”는 이 식과 정확히 일치하지 않아 근사 설명으로만 취급합니다.

초기 발표는 개수 질문에 더 큰 입력을 설명하지만 제공 CFG의 `COUNT_MULT=1.0`이므로 현재 코드는 개수 유형에 추가 배율을 주지 않습니다. Gemma의 560은 프로세서 soft token 설정이며 Qwen 토큰과 같은 픽셀 면적이라고 환산할 수 없습니다. Gemma 로더는 존재하는 여러 이미지 프로세서 속성에 그 값을 적용하므로 실제 패치·토큰 수는 실행으로 확인해야 합니다.

근거: 코드 전용 셀 7·8의 `PS`, `tokens_for`, `load_image`, 셀 12의 `gemma_load`; 초기 발표 슬라이드 3.
